## Refined Class Diagram (1 class)

### AlertLog

```
┌──────────────────────────────────────────────┐
│                AlertLog                      │
├──────────────────────────────────────────────┤
│ - log_id: UUID                               │
│ - pond_id: UUID                              │
│ - project_id: UUID                           │
│ - timestamp: Timestamp                       │
│ - log_type: String                           │
│ - message: String                            │
│ - severity: String                           │
│ - parameter: String                          │
│ - reading_timestamp: Timestamp               │
│ - acknowledged: Boolean                      │
│ - acknowledged_by: UUID                      │
│ - acknowledged_at: Timestamp                 │
│ - resolved: Boolean                          │
│ - resolved_by: UUID                          │
│ - resolved_at: Timestamp                     │
├──────────────────────────────────────────────┤
│ + acknowledge(user_id: UUID): void           │
│ + resolve(user_id: UUID): void               │
│ + is_acknowledged(): Boolean                 │
│ + is_resolved(): Boolean                     │
│ + is_pending(): Boolean                      │
│ + get_pond(): Pond                           │
│ + get_project(): Project                     │
└──────────────────────────────────────────────┘
```

**Methods:**
- `acknowledge(user_id)` — sets `acknowledged = true`, `acknowledged_by = user_id`, `acknowledged_at = now`
- `resolve(user_id)` — sets `resolved = true`, `resolved_by = user_id`, `resolved_at = now`
- `is_acknowledged()` — returns `acknowledged` flag
- `is_resolved()` — returns `resolved` flag
- `is_pending()` — returns `true` if not acknowledged AND not resolved (needs attention)
- `get_pond()` — returns the pond that generated this alert
- `get_project()` — returns the project this alert belongs to

## Relationships

```
Pond "1" ──────── "*" AlertLog           : generates     (Association)
Project "1" ──── "*" AlertLog            : belongs to    (Association)
User "1" ──────── "*" AlertLog           : acknowledges  (Association — acknowledged_by)
User "1" ──────── "*" AlertLog           : resolves      (Association — resolved_by)
```

### Why Association (not Composition)?

| Relationship | Type | Why |
|---|---|---|
| Pond → AlertLog | **Association** | Although alerts CASCADE on pond delete, alerts are not "part of" a pond conceptually. They are events generated by sensor readings. Alerts have independent business value (audit trail, history). |
| Project → AlertLog | **Association** | Same reasoning — alerts reference the project but are independent records. |
| User → AlertLog | **Association** | User is just referenced as who acknowledged/resolved. No ownership. |

> **Why not Composition?** Even though the FK is CASCADE, alerts are **historical records** with audit value. In practice you'd rarely delete a pond/project with active alerts. Association better represents the conceptual relationship — alerts are events that happen to a pond, not parts of a pond.

## Alert Lifecycle

```
1. Sensor reading received
       ↓
2. SensorReading.check_thresholds() detects violation
       ↓
3. AlertLog created:
   - log_type = 'alert'
   - severity = based on how far outside threshold
   - parameter = which parameter violated
   - acknowledged = false
   - resolved = false
       ↓
4. User sees alert on frontend → clicks Acknowledge
   - AlertLog.acknowledge(user_id)
       ↓
5. User fixes the issue → clicks Resolve
   - AlertLog.resolve(user_id)
```
