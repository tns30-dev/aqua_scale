## Slide content (what appears on the slide)

### Title
**Project Backlog — User Stories by Epic**

### Body — backlog table

**Epic 1 · Authentication & User Management**

| ID | User Story |
|---|---|
| US-01 | As a user, I want to sign in and out securely so that my session is protected. |
| US-02 | As a user, I want to view my own profile so that I can confirm my account details. |
| US-03 | As a user, I want to update my own profile (name, mobile, password) so that my information stays current. |
| US-04 | As a platform admin, I want to onboard new users with a default feature-access set so that new staff can start working immediately. |
| US-05 | As a platform admin, I want to manage another user's feature access and action controls so that permissions match each user's responsibilities. |
| US-06 | As a platform admin, I want to assign users to one or more projects so that they only see ponds in projects they own. |
| US-07 | As a platform admin, I want to deactivate a user account without deleting it so that I preserve audit history. |

**Epic 2 · Pond Operations**

| ID | User Story |
|---|---|
| US-08 | As a farm manager, I want to see all my ponds and their current health status on one overview screen so that I can spot problems at a glance. |
| US-09 | As a farm manager, I want to view a digital twin of each pond so that I can see live water-quality parameters in context. |
| US-10 | As a farm manager, I want to view real-time and forecasted parameter trends so that I can plan adjustments before conditions degrade. |
| US-11 | As a farm manager, I want to compare multiple ponds side by side over a chosen date range so that I can learn what's working in my best-performing pond. |
| US-12 | As a farm manager, I want a parameter-summary comparison and a comparison chart so that I have both tabular and visual views of the comparison. |

**Epic 3 · Cycle & Growth Management**

| ID | User Story |
|---|---|
| US-13 | As a farm manager, I want to start a new growth cycle for a pond so that all subsequent readings are attributed to that cycle. |
| US-14 | As a farm manager, I want to record daily health observations for each cycle so that I have a per-day record of growth quality. |
| US-15 | As a farm manager, I want to advance a cycle through its lifecycle stages (juvenile · grow-out · pre-harvest) so that the platform tracks where each pond is in its cycle. |
| US-16 | As a farm manager, I want a cycle-health overview that aggregates alerts and key indicators by cycle so that I can review the cycle's full health story when it closes. |

**Epic 4 · Sensor & IoT Management**

| ID | User Story |
|---|---|
| US-17 | As a system admin, I want to register IoT devices (code, status, configuration) so that incoming MQTT messages are accepted only from known devices. |
| US-18 | As a system admin, I want to declare sensor types (model number, manufacturer, parameters measured) so that the platform knows what each sensor reports. |
| US-19 | As a system admin, I want to attach project sensors to specific ponds with GPS coordinates and an installed datetime so that readings are spatially located. |
| US-20 | As a system admin, I want to activate or deactivate a sensor without deleting it so that I preserve historical data when a sensor is taken offline. |
| US-21 | As a system admin, I want incoming sensor messages to be archived (raw + parsed) so that any reading can be traced back to the original payload. |

**Epic 5 · Visualisation & Historical Trends**

| ID | User Story |
|---|---|
| US-22 | As a system admin, I want to declare visualisation types (chart type, required parameters) so that visualisations are reusable across projects. |
| US-23 | As a system admin, I want to configure project-level visualisations (which chart, which X/Y parameters, enable/disable) so that each project's dashboard reflects its parameter set. |
| US-24 | As a farm manager, I want to view multi-parameter historical trends with selectable time-range grouping (hourly · daily · weekly · monthly) so that I can analyse trends at the right resolution. |
| US-25 | As a farm manager, I want to export historical data filtered by date range so that I can share it with external advisors or research collaborators. |

**Epic 6 · Alerts & Notifications**

| ID | User Story |
|---|---|
| US-26 | As a farm manager, I want real-time alerts when a parameter crosses its safe threshold so that I can act before stock is lost. |
| US-27 | As a farm manager, I want to acknowledge alerts so that I can clear my dashboard once an issue is being handled. |
| US-28 | As a farm manager, I want every alert logged with its parameter, severity, and reading timestamp so that there is an audit trail of every incident. |

**Epic 7 · Treatment Management**

| ID | User Story |
|---|---|
| US-29 | As a farm manager, I want to record treatments applied to a pond (chemical, dosage, timestamp) so that the platform tracks what was done and when. |
| US-30 | As a farm manager, I want to evaluate treatment effectiveness by comparing pre- and post-treatment parameter readings so that I can decide whether the treatment worked. |
| US-31 | As a farm manager, I want to view a treatment history per pond so that I can avoid repeating an ineffective treatment. |

**Epic 8 · Project & Profile Configuration**

| ID | User Story |
|---|---|
| US-32 | As a system admin, I want to define profile types (shrimp · fish · crab hatchery) so that each farm type has its own schema of parameters and growth stages. |
| US-33 | As a system admin, I want to create projects and assign owners so that the platform supports multi-tenant farm operations. |
| US-34 | As a system admin, I want to add ponds (with metadata + image) under a project so that operators can identify each pond visually. |
| US-35 | As a system admin, I want to declare parameter types (name, unit, data type) so that readings are interpreted consistently across projects. |
| US-36 | As a system admin, I want to set min/max thresholds per project-parameter so that the alerting engine knows what "safe range" means per farm. |

**Epic 9 · Security & Compliance**

| ID | User Story |
|---|---|
| US-37 | As a security-conscious operator, I want authentication tokens stored in HttpOnly cookies so that XSS cannot exfiltrate my session. |
| US-38 | As a security-conscious operator, I want CSRF protection on state-changing endpoints so that cross-site requests cannot act on my behalf. |
| US-39 | As a platform admin, I want all sensitive secrets (DB password, JWT key) stored in Secret Manager rather than env files so that they never appear in logs or images. |
| US-40 | As a platform admin, I want every dependency scanned for known CVEs on every PR so that vulnerable packages don't ship to production. |
| US-41 | As a platform admin, I want static + dynamic security scanning (SAST + DAST) in the pipeline so that source-level and runtime issues are caught before deploy. |

**Epic 10 · Infrastructure & DevOps**

| ID | User Story |
|---|---|
| US-42 | As a developer, I want unit and end-to-end tests to run on every PR so that regressions are caught before merge. |
| US-43 | As a developer, I want load and stress tests in CI so that performance changes are visible per commit. |
| US-44 | As a platform admin, I want the GCP infrastructure provisioned via Terraform so that the environment is reproducible and tear-down is one command. |
| US-45 | As a platform admin, I want a containerised, scale-to-zero deploy on Cloud Run so that the demo environment costs almost nothing between sessions. |

## Speaker notes (≈ 75–90s — say out loud, don't put on slide)

> "The backlog comes to fifty-three user stories across twelve epics. Ten of those epics are delivered or in progress — that's the work I'll walk through on the technical slides. The last two epics are planned for the next delivery cycle.

> The largest delivered epic, **Authentication and User Management**, is seven stories — went through three implementation iterations, ending in the consultant-driven schema rename.

> **Pond Operations** covers the farm manager's day: overview, digital twin, real-time + forecast trends, and the multi-pond comparison feature.

> **Cycle and Growth Management** tracks each pond through its lifecycle from cycle start through stage advancement to closing health overview.

> **Sensor and IoT Management** is the configuration layer that supports the MQTT pipeline — IoT registration, sensor types, project-sensor wiring with GPS.

> **Visualisation and Historical Trends** is how historical data surfaces — declared types, configured per project, viewed with selectable time grouping, exportable.

> **Alerts and Notifications** is the live-incident workflow today — threshold alerts, acknowledgement, audit log.

> **Treatment Management** captures what was applied, evaluates effectiveness against parameter readings, and surfaces a per-pond history.

> **Project and Profile Configuration** is the platform-setup layer — profile types, projects, ponds, parameter types, thresholds.

> **Security and Compliance** plus **Infrastructure and DevOps** — nine stories total — cover HttpOnly cookies, CSRF, Secret Manager, SCA, SAST and DAST, tests in CI, Terraform IaC, and Cloud Run.

> The two planned epics — **Notification Service** for multi-channel alert delivery, and **Model Integration** for predictive analytics — are scoped but not yet started. They represent the next cycle and complete the roadmap on slide 3."
