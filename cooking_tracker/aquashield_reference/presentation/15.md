## Slide content (what appears on the slide)

### Title
**Security — Three Planes, Layered Controls**

### Layout — three-column table

| 🎨 Frontend (browser) | ⚙️ Backend (Cloud Run) | 📡 Communication (in transit) |
|---|---|---|
| **HttpOnly + Secure JWT cookies** — XSS cannot read tokens | **Django Secret Manager mount** — runtime secrets injected at boot, never in env files or images | **HTTPS / TLS 1.2+ everywhere** — Cloud Run terminates TLS at the edge; `SECURE_PROXY_SSL_HEADER` honoured by Django |
| **CSRF double-submit token** — `csrftoken` cookie + `X-CSRFToken` header on every state-changing request | **CORS allow-list** — `CORS_ALLOWED_ORIGINS` pinned to the frontend Cloud Run URL · `CORS_ALLOW_CREDENTIALS = True` | **MQTT over TLS 8883** — broker accepts no plaintext; Pi presents a TLS cert |
| **Content-Security-Policy + X-Content-Type-Options + X-Frame-Options** (nginx headers) | **CSRF middleware + `CSRF_TRUSTED_ORIGINS`** — verifies same-site or trusted-cross-site origin | **`SameSite=None ; Secure` on cookies** — required cross-site for the GCP demo (`*.a.run.app` on Public Suffix List); deliberate trade-off |
| **Input validation via Zod** — every form schema validated client-side before submit (defence in depth, not the source of truth) | **DRF input validation** — server-side serializers are the source of truth; deserialisation rejects malformed payloads | **Cloud SQL Auth Proxy** — backend → DB connection runs over Google-managed TLS, no public IP exposed |
| | **Bandit (SAST) · pip-audit (SCA) · OWASP ZAP (DAST)** in CI — every PR | **Cloud Run IAM + VPC firewall** — only `443` (HTTPS) and `8883` (MQTT-TLS) ingressed publicly |

### Caption (one line)

*Defence in depth — no single control is the gate. Even if XSS sneaks in, HttpOnly cookies stop token theft; even if CSRF token leaks, SameSite stops cross-site replay; even if the broker is reached, TLS + IAM stop unauthorised publish.*

## Speaker notes (≈ 60s — say out loud, don't put on slide)

> "Three planes — frontend, backend, communication — each with two to four concrete controls.

> **On the frontend**, the most important control is **HttpOnly + Secure JWT cookies**. We deliberately *don't* put the token in `localStorage` where XSS could exfiltrate it. We pair that with **CSRF double-submit** — a non-HttpOnly cookie plus an `X-CSRFToken` header — and standard browser hardening headers from nginx.

> **On the backend**, runtime secrets are pulled from **GCP Secret Manager** at boot, not from environment files baked into the image. CORS is pinned to the frontend's Cloud Run URL, with credentials allowed because cookies cross origins on the GCP demo. **Bandit, pip-audit, and OWASP ZAP** run in CI on every PR, so security findings surface before merge.

> **On the wire**, everything is **TLS** — HTTPS at Cloud Run's edge, MQTT-over-TLS on port 8883 to the broker, Cloud SQL Auth Proxy between backend and Postgres. The one trade-off worth naming is **`SameSite=None`** on cookies — we needed it because Cloud Run's `*.a.run.app` is on the Public Suffix List, so frontend and backend are cross-site from the browser's perspective. We accept that and rely on the `Secure` attribute plus CORS allow-list to compensate.

> The principle across all three planes is **defence in depth** — no single control is the gate."

## Notes for the panel (if asked)

- *Why HttpOnly cookies instead of `Authorization: Bearer`?* — Bearer tokens in `localStorage` are reachable by any XSS that runs in the page. HttpOnly cookies are not. The trade-off is CSRF, which we handle with double-submit.
- *Why is `SameSite=None` acceptable here?* — It's only enabled on the GCP demo (different runtime hostnames per Cloud Run service). On the production deploy (single domain) we use `SameSite=Strict`. The relaxation is environment-scoped via the `JWT_COOKIE_SAMESITE` Django setting.
- *What stops an attacker who registers a malicious IoT device?* — MQTT broker authentication (username + password) plus TLS client-cert verification. The `module_sensor` admin layer also requires the `IotDevice` record to exist before its messages will be accepted by the ingest path.
- *How are sensitive secrets handled in CI?* — GitHub Secrets at the workflow level; never echoed; injected via `${{ secrets.* }}` references only. GCP runtime secrets live in Secret Manager and are mounted into Cloud Run via `--set-secrets` — they never appear in the container image.
