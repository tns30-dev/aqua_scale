## 1. Scope

Following the teacher's note, the GCP demo deployment is provisioned via
**Terraform**, not by clicking through the GCP console. The Terraform
module lives in:

```
infra/terraform/
├── versions.tf      # tf + provider versions
├── main.tf          # provider config
├── variables.tf     # inputs (project, region, secrets)
├── apis.tf          # enable required GCP APIs
├── registry.tf      # Artifact Registry repo
├── database.tf      # Cloud SQL Postgres 15 instance + db + user
├── secrets.tf       # Secret Manager entries for django/jwt/db
├── iam.tf           # deploy SA + role bindings + key
├── outputs.tf       # AR URL, Cloud SQL connection name, SA key
├── terraform.tfvars.example
└── .gitignore       # tfstate + tfvars never committed
```

**What Terraform owns (foundational infra):**

| Resource | Terraform resource |
|---|---|
| Required GCP APIs (run, artifactregistry, sqladmin, secretmanager, cloudbuild, iamcredentials) | `google_project_service` |
| Container registry | `google_artifact_registry_repository` |
| Database — Cloud SQL Postgres 15, `db-f1-micro` | `google_sql_database_instance` + `google_sql_database` + `google_sql_user` |
| Runtime secrets (DJANGO_SECRET_KEY, JWT_SECRET_KEY, DB_PASSWORD) | `google_secret_manager_secret` + `_secret_version` |
| Deploy service account + IAM bindings | `google_service_account` + `google_project_iam_member` |
| Deploy SA JSON key (output, sensitive) | `google_service_account_key` |

**What Terraform does NOT own (intentional split):**

| Excluded | Why |
|---|---|
| Cloud Run services (`backend-svc`, `frontend-svc`) | Owned by the CI/CD deploy workflows. Cloud Run revisions change on every deploy — Terraform shouldn't fight them. Cloud Run auto-creates the service on first `gcloud run deploy`. |
| Container images | Built and pushed by `deploy-gcp-*.yml`. Image lifecycle ≠ infra lifecycle. |
| Database **seed data** | Loaded once with `gcloud sql import sql` from `backend/sql/aquashield_current_local_share.sql`. The seed file is INSERT-based Postgres SQL, brittle to express as Terraform `local-exec`. |
| GitHub Actions secrets | Live in GitHub's secret store, not in Terraform state. The SA key is *output* by TF but pasted into GH manually. |

## 2. Standard lifecycle

```bash
cd infra/terraform

# one-time init
terraform init

# fill in sensitive values
cp terraform.tfvars.example terraform.tfvars
# edit terraform.tfvars — set database_password, django_secret_key, jwt_secret_key
# (or pass via TF_VAR_database_password=... env vars; tfvars file is gitignored)

# preview
terraform plan

# apply
terraform apply

# grab outputs
terraform output -raw deploy_sa_key | base64 -d   # → paste into GitHub secret GCP_SA_KEY
terraform output cloudsql_connection_name        # → matches CLOUDSQL_INSTANCE in deploy-gcp-backend.yml
terraform output artifact_registry_url           # → matches IMAGE prefix in both deploy workflows

# tear down after the presentation
terraform destroy
```

`terraform destroy` removes everything except the GitHub secrets (those
stay in GitHub) and the seed SQL file (that lives in the repo).

## 3. Why this layout

### Foundational infra in Terraform; runtime services in CI/CD

The split avoids a common pain point: Terraform and `gcloud run deploy`
both want to be the source of truth for a Cloud Run service. If both touch
the same service, every CI deploy shows a Terraform drift, and every
`terraform apply` resets the image. By keeping Cloud Run services entirely
in the deploy workflows, both sides stay clean:

- Terraform = **state of the platform** (registry, DB, secrets, IAM)
- Deploy workflows = **state of the deployed app** (image tag, env vars, scaling)

### Secrets in Terraform variables, not in code

`terraform.tfvars` is gitignored. Sensitive variables are marked
`sensitive = true` so they never appear in plan output. Real values are
either pasted into `terraform.tfvars` locally or passed via
`TF_VAR_<name>` env vars during apply. The values themselves end up in
**Secret Manager** (managed by Terraform), and Cloud Run pulls them at
runtime via `--set-secrets`.

### State storage

For the demo: local state file (`*.tfstate`), gitignored. For a real prod
setup we'd use a GCS backend with state locking — out of scope here, but
swappable by adding a `backend "gcs" { ... }` block to `versions.tf`.
