## Speaker notes (≈ 60s — say out loud, don't put on slide)

> "Three architectural constraints shaped almost every choice in the platform.

> **First — the IoT edge has to tolerate offline periods.** Pond networks drop out. Sensors can't lose data while the broker is unreachable. That's why we run **Raspberry Pi with Mosquitto MQTT** in-house — the Pi buffers locally and replays when the broker is back. The broker sits on the same VM as the Django backend, so the round-trip from sensor to database is short and observable.

> **Second — we deliberately chose not to use a cloud-provider IoT service.** I evaluated AWS IoT Core and Azure IoT Hub in Sprint 4 and concluded that for our cost and control needs, self-hosting was the right call. We avoid per-message billing, vendor SDKs on the edge, and any future lock-in.

> **Third — and this is the biggest one — the project is being unified with a sister product, BioBloc, into a single subscription-based platform.** Different tenants will need different feature sets and different farm profiles. To make that work without rewriting the schema every time, we put **feature access into a JSONB column on the user table**, alongside a similar JSONB for action-level controls. Profile types — shrimp, fish, crab hatchery today, BioBloc profiles next — plug into the same schema without table changes.

> Those three constraints — offline IoT, no cloud-IoT lock-in, and subscription-driven multi-tenancy — drove the rest of the architecture you'll see in the next two slides."

## Notes for the panel (if asked)

- *Why not AWS IoT Core?* — Compared head-to-head against AWS IoT Core and Azure IoT Hub in Sprint 4. AWS wins on managed reliability; we win on cost, offline buffering on the Pi, and not requiring vendor SDKs at the edge.
- *Why JSONB for feature access?* — Different subscription tiers expose different module + action combinations; expressing that as 1:N tables would require schema changes per new tier. JSONB keeps the user table stable while the data shape per row evolves.
- *How does this support BioBloc?* — BioBloc is the next product line — different farm types (bio-bricks for water filtration), different parameter sets — but the same operator workflows. The multi-profile schema and the subscription-keyed feature access were designed with BioBloc in mind from Sprint 2 onward.
